# 문제 해결 기록

아래 내용은 현재 코드, 테스트, Git 기록 또는 2026-09-26 기준 점검으로 확인한 사실만 기록한다.

## 1. 검색 첫 결과가 현재 학기 정답이 아닐 수 있음

- 문제: 게시판 검색 결과 순서만 따르면 과거 학기나 다른 프로그램 공지를 선택할 수 있다.
- 재현 방법: `tests/searchService.test.ts`, `scoreCandidate`의 연도·학기·제외어 조건 확인.
- 초기 가설: 키워드 포함 여부만으로 충분할 수 있다.
- 시도한 접근: 제목/부서 키워드, 연도, 학기, 게시일을 점수화했다.
- 실패한 접근: 검색 결과의 첫 항목을 그대로 답으로 쓰는 방식은 근거가 약하다.
- 확인한 원인: 게시판 검색 순서와 질문의 적용 학기·의도는 동일하지 않다.
- 선택한 해결책: 현재 연도 +12, 학기 +3, 핵심 키워드 +6, OCU·학점교류·대학원 등 비대상 공지 -12 규칙을 적용한다.
- 검증 방법과 결과: `tests/searchService.test.ts`의 후보 점수화 테스트 통과.
- 남은 한계: 제목에 연도·학기가 없거나 표현이 바뀌면 점수 조정이 필요하다.

## 2. 계절학기·일반 키워드로 일정이 잘못 선택될 수 있음

- 문제: `일정`, `시험` 같은 넓은 표현만으로는 중간고사와 다른 일정을 구분하기 어렵다.
- 재현 방법: `calendarMatches`와 `tests/pageFetcher.test.ts` 확인.
- 초기 가설: 현재 연도 일정 중 첫 항목을 선택한다.
- 시도한 접근: `중간시험`을 `중간고사`로 정규화하고, 월로 학기를 추정하며 핵심 키워드를 비교한다.
- 실패한 접근: 넓은 일정 키워드만 사용하면 관련 없는 일정이 포함될 수 있다.
- 확인한 원인: 공식 학사일정 용어와 학생 질문 용어가 다르고 한 응답에 여러 학기가 포함된다.
- 선택한 해결책: 연도·학기·정규화된 주제어를 모두 만족하는 항목만 선택한다.
- 검증 방법과 결과: 2026년 1·2학기 fixture 중 2학기 중간시험만 선택하는 테스트 통과.
- 남은 한계: 학기 경계 월이나 새로운 명칭은 규칙 보강이 필요하다.

## 3. SSRF와 외부 redirect 위험

- 문제: 외부 HTML의 링크 또는 사용자 질문의 URL을 그대로 요청하면 내부망·비공식 호스트 접근 위험이 있다.
- 재현 방법: `tests/domainValidator.test.ts`, `tests/searchService.test.ts` 실행.
- 초기 가설: `scnu.ac.kr` 문자열 포함 확인으로 충분할 수 있다.
- 시도한 접근: URL 파싱 후 HTTPS, 정확한 hostname, 허용 path, 포트, 인증정보, IP literal을 검사했다.
- 실패한 접근: suffix/substring 검사는 `scnu.ac.kr.attacker.example`을 막지 못할 수 있다.
- 확인한 원인: 최초 URL뿐 아니라 redirect 목적지도 신뢰 경계를 넘을 수 있다.
- 선택한 해결책: `redirect: manual`, 최대 2회, 매 단계 Allowlist 재검증을 적용한다.
- 검증 방법과 결과: 허용 redirect 성공, 공격자 호스트 redirect·localhost·IP·비표준 포트 차단 테스트 통과.
- 남은 한계: 공식 사이트가 새 경로로 이동하면 Allowlist를 검토해 명시적으로 추가해야 한다.

## 4. 기본 테스트가 실제 외부 사이트에 의존함

- 문제: `tests/chatRoute.test.ts`의 도서관 질문이 기본 `fetch`를 사용해 네트워크 상태에 따라 지연·실패할 수 있다.
- 재현 방법: 테스트에서 `chatRoute.request` 호출 후 검색/원문 Fetch 의존성 경로 확인.
- 초기 가설: 공식 사이트가 안정적이므로 단위 테스트에서도 호출 가능하다.
- 시도한 접근: 개별 서비스에는 이미 fetcher 주입을 일부 사용했다.
- 실패한 접근: timeout만 늘리면 테스트 속도와 재현성이 계속 외부 상태에 좌우된다.
- 확인한 원인: 라우트가 구체 서비스 함수를 직접 호출해 테스트에서 전체 의존성을 교체하기 어렵다.
- 선택한 해결책: 작은 resolver 팩토리/의존성 주입으로 기본 테스트는 fixture만 사용하고 실제 사이트는 `test:live`로 분리한다.
- 검증 방법과 결과: 라우트 resolver를 fixture로 주입했고 기본 테스트 54개가 외부 인터넷 없이 통과했다. 실제 사이트 확인은 `npm run test:live`로 분리해 1개가 통과했다.
- 남은 한계: live 테스트는 공식 사이트 상태에 따라 실패할 수 있으며 배포 차단 조건으로 쓰지 않는다.

## 5. 공개 URL이 HTTP 200이어도 장애 본문일 수 있음

- 문제: 과거 점검에서 `Site Unavailable` 본문이 보고되어 상태 코드만으로 서비스 성공을 판단할 수 없다.
- 재현 방법: `curl -L -D -`로 헤더와 본문, `/api/health` Content-Type을 함께 확인한다.
- 초기 가설: HTTP 200이면 정상이다.
- 시도한 접근: 루트 HTML 식별자와 Health JSON을 함께 검사했다.
- 실패한 접근: 상태 코드만 검사하면 플랫폼 오류 페이지를 정상으로 오판한다.
- 확인한 원인: 과거 장애의 플랫폼 내부 원인은 현재 저장소 기록만으로 확인할 수 없어 `추가 확인 필요`다.
- 선택한 해결책: 본문·Content-Type·실제 UI를 배포 판정 조건에 포함한다.
- 검증 방법과 결과: 2026-09-26 20:03 KST에는 실제 앱 HTML과 `status: ok` JSON을 확인했다.
- 남은 한계: 간헐 장애 탐지를 위한 지속 모니터링은 아직 없다.

## 6. Worker와 브라우저에서 공식 게시판 요청이 다르게 동작한 문제

- 문제: 지시서에 과거 사례로 제시되었으나 원인과 실패 로그는 현재 Git 기록에서 확인되지 않는다.
- 재현 방법: 추가 확인 필요.
- 초기 가설: User-Agent, Referer, redirect, 플랫폼 egress 차이 가능성이 있다.
- 시도한 접근: 현재 코드는 공식 Referer/User-Agent와 수동 redirect를 사용한다.
- 실패한 접근: 확인 가능한 기록 없음.
- 확인한 원인: 추가 확인 필요.
- 선택한 해결책: 실패 종류와 HTTP 상태를 구조화해 이후 로그로 근거를 남긴다.
- 검증 방법과 결과: 로컬 fixture와 선택적 live 테스트를 분리한다.
- 남은 한계: 실제 Worker 환경 차이는 배포 후 재검증해야 한다.
